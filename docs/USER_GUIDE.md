# 用户使用指南：在企微群里把事情说清楚

在管理员接入并授权的工作群里，找到管理员指定的助手，在企业微信输入框中选择并 @ 它，再用平常说话的方式提问。你不需要先判断这是咨询、Bug 还是需求，也不用背机器编号或路由口令。

本文介绍接入后的使用方式；是否已接通、适用哪个项目，以管理员公布的范围为准。网站本身不会接入新群。

## 先从一句话开始

下面的“@助手”是示意：请在企微界面选择本群实际的机器人，不是只输入一段看起来像 @ 的文字。

|你想做什么|可以这样说|
|---|---|
|问用法|@助手 我想把本月的记录导出来，应该从哪里操作？|
|报告问题|@助手 我在列表选了本月，再点导出，只下载到了第一页。预期是全部结果，今天试了两次都这样。|
|提出需求|@助手 每周都要手动整理导出记录，能不能按日期一次导出？这样可以少做很多重复整理。|

说清楚正在做什么、哪个页面或功能，以及卡在哪里就可以。报问题时，已知的话补充操作步骤、预期和实际结果；提需求时，说明想解决的场景和希望得到的结果。不知道根因、方案或实现成本，也可以先提出。

不要在群里发密码、令牌、客户隐私、私有源码或完整原始日志。需要截图或其他资料时，先脱敏并使用管理员允许的方式；助手当前不承诺直接识别或转发图片、文件、语音。

## 助手会怎么处理

- **先确认接收。** 正常收到后会尽力给“收到，稍等”这样的短回执。这只表示接收或正在转交，不代表问题已分析完成。
- **能解释就先解释。** 咨询可能直接得到用法或当前行为的说明，不必每次都建单；依据不足时会说明还不知道什么。
- **缺信息再问。** 每轮通常只补问一两项关键事实，例如“导出前是否设置了日期范围？”不用把已经说过的整段再发一遍。
- **需要改动再登记。** 助手会查找已有同类事项；需要且有权限新建时，将 Bug 或需求整理进 GitHub Issues，确认成功后才给登记回执，必要时附你有权访问的链接。已有同类事项时会说明关联，不重复建单。

回复速度和可用能力取决于实际接入、平台及响应方状态。没有回执或迟迟没有结果时，先确认群已接入、@ 的是正确助手，再请管理员核对；不要连续大量重发同一内容。

## 怎样补充上一件事

继续 @ 助手，并自然点明事项，再回答它缺的部分。例如：

> @助手 关于刚才“导出只到第一页”的问题，日期已经选了整个月，但文件里仍只有20条。

> @助手 关于按日期一次导出的需求，最常用的是每周一整理上一周的数据。

需要时可以带上事项短标题，或允许公开的 Issue 链接；不用背内部消息编号。只写“是的”“上面那个”可能无法判断指的是哪件事，助手会再确认。

每条企微文本可能作为一次新请求处理，上下文也可能不完整。不要依赖原生引用自动对应、长期记忆或同一个人自动续聊；简短点明事项有助于正确关联。回复别人的群消息或不 @ 助手，不保证机器人能收到。助手回复按已批准私有映射核验当前发送者姓名后，以普通姓名和事项开头；未知则省略姓名、点明事项，不催补身份。助手不做真正提及、纯文本 @ 或 @ 测试。

## 登记以后，会发生什么

登记回执表示事项已被记录，**不等于负责人采纳、排期、开始开发或承诺上线**。负责人会评估采纳、暂缓或拒绝；决定实施时，还要明确范围并取得相应授权。

可以自然询问：

> @助手 关于按日期导出的需求，现在有可以公开的进展吗？

助手只能说明有证据且允许在群里公开的状态；私聊、评审正文和内部执行细节不会默认公开。无法确认的进度会保留未知，不能把登记成功当作已经完成。

HiveFlow 当前的自动开发尚未启用。群里说“可以”“同意”或提出新反馈，都不能让助手绕过授权去修改代码、部署或执行其他操作。

## 背后复用了什么

你在企业微信沟通，独立的 wecom-slack-bridge 负责消息传输；Dots 负责理解、调查与协调，复用账号可用的先进模型能力；Bug 和需求由 GitHub Issues 管理。具体模型以账号和平台支持为准，不要求用户先学习这些工具或选择模型。

如需理解负责人如何决定和交付，阅读 [核心流程](WORKFLOW.md)；接收方的详细规则见 [群入口](GROUP_INTAKE.md)，工具边界见 [适配说明](ADAPTERS.md)。
