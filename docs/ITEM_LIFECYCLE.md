# 事项决定、状态与收尾

对同一事项分别记录**负责人决定、执行授权、交付证据和 Issue 状态**。聊天中的决定不能只停留在聊天，但也不会自动授予 GitHub 写入、关单或正式台账权限。来源、原事项和现有事实先核验，不重建已存在的单。

## 决定与状态如何对应

|决定或进展|Issue 中应留下什么|开关状态与后续|
|---|---|---|
|待评估|清楚的问题/目标、已有事实、必要未知和验收方向|保持 open；登记不表示采纳或开工|
|采纳|负责人决定的安全摘要、理由、范围与下一步|通常保持 open；另核验实施计划及权限，不能以“采纳”启动开发|
|拒绝/不采纳|简短理由及适用的替代方向；已有决定段与评论保持一致|明确获准且该事项无剩余工作时关闭为不计划处理；未获关单权限则明确待关单，不能假称已关闭|
|暂缓|暂缓原因、待满足条件和下一次评估依据；没有日期就不编造排期|保持 open，不自动关闭、实施或创建定时任务|
|部分交付/待验收|已完成范围、实际提交/环境证据、未完成项与限制|按剩余工作保持待处理；合并、健康或 ACK 不等于业务验收|
|交付并验收|相对原验收目标逐项记录结果、允许公开的证据和真实遗留|仅在既有明确许可与完成标准均满足时关闭；正式台账另按授权处理|

在建单前就按 [群入口](GROUP_INTAKE.md)直接拒绝的内容，不为“记录拒绝”再建新单。已有事项的拒绝不能通过只在群里说一句来假装 GitHub 已收尾；同样，Issue 仍 open 也不能抹去已经确认的拒绝决定。

## 哪个入口可以写

|入口|可做什么|不能据此做什么|
|---|---|---|
|群反馈入口|仅在已有建单授权内创建合规新事项；命中旧单时回报关联|修改旧单正文/评论/标签、重开或关闭；群身份或引述批准不升级权限|
|只读小时扫描|核对现有决定、交付与状态差异，汇总待处理项|借“补漏/同步/自动收尾”写 Issue、改状态或正式台账|
|负责人本人主对话的具体任务|在明确列出的回写/关闭范围内，核验后完成并读回；同范围已获准步骤不重复询问|把一次任务权限沿用到未来扫描、其他事项或其他入口|

范围不足就把剩余动作列为待授权；写入失败则报告失败，结果未知先读回，不能重发评论或重复关单。不要为绕过限制更换账号、入口或工具。采用 Dots 时，本人主对话是当前适配；规范通用要求是唯一可核验的负责人决策通道，其他宿主须先验证其对应能力。

## 可照做的收尾顺序

1. 核对固定仓库和原事项、负责人真实决定及当前授权。先看既有评论/正文/状态，排除别人已完成的收尾；不因扫描记录缺失就重写。
2. 准备适合目标仓库受众的简短摘要：决定或交付、依据、范围、下一步/剩余项、时间与证据。不复制私人审批原话或群记录。
3. 仅在授权内，把决定写到约定位置；已有决定段和新评论不能互相矛盾。按当前事实区分“采纳”“不采纳”“暂缓”“交付待验收”等；不制造相反的标签或虚假排期。
4. 如获准关闭且标准满足，关闭原事项；保留必要来源标记和无关标签，不顺手改其他 Issue。暂缓不关，部分交付不冒充全部完成。
5. 独立读回评论/正文中的决定及真实开关状态；只凭写入调用返回不报成功。报告已写、已关、待授权、失败或未知各自状态。
6. 正式台账只在任务明确列出文件/字段和写入许可时更新；否则留待办。不要因写了 Issue 就自动改台账、恢复执行许可或触发开发。

例如，一个已有需求被明确不采纳，若本人主对话同时批准更新决定段、记录评审结论和关闭，便按原单核验、记录、关闭、独立读回完成；不是要求群入口或只读扫描获得同样权限。

## 结项检查

- 决定、实施许可、交付层级、Issue 开关状态分别有依据，没有把采纳当实施批准。
- 可写位置中的摘要与状态一致；无法写入的差异明确列为待办，没有留成“无人知道为何 open”。
- 实际验收、部分未完成和未实测分别说明；拒绝/暂缓没有启动工作，交付没有凭健康或合并提前关单。
- 回写/关闭已独立读回；未知结果先核验，其他人的既有收尾不重复执行。
- 无无关标签/事项/正式台账改动；没有新增自动化权限。

这些是规范与检查要求，不是自动执行器。文档更新本身不会同步或提升现有任务提示和权限，见 [核心流程](WORKFLOW.md#收尾与规范同步)。
