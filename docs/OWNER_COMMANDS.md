# 清楚、简短地沟通

## 群回复

按 [姓名契约](GROUP_INTAKE.md#发送者姓名与私有映射)核验成功时先用普通“姓名，关于你问的某问题……”称呼，未知则省略姓名并点明事项；随后先给结论或当前已确认状态，再补必要解释。每次问 1–2 个关键缺口，不重复用户已提供的信息；不展示内部身份/请求 ID，不做真正提及、纯文本 @ 或 @ 测试，不承诺提醒已送达。桥接负责传统收到回执，dots 不另发重复的收到确认；登记回执另按 [查重与可读登记](GROUP_INTAKE.md#查重与可读登记)检查原根并完成，不以 dots 汇报代替。

已有查证时，群答复和登记回执按 [回复方式](GROUP_INTAKE.md#回复方式)在同一条中附 2–3 点必要初步分析，区分证据、判断与未知；不只报编号，不碎片播报。

以下均为姓名未知时的合成表达示例；姓名已核验则按上述格式加称呼，不是实际建单、实施许可或验证结果：

|场景|示例|
|---|---|
|咨询可解决|“关于登录页标题：这是当前页面配置的公司名称，可从设置页查看完整信息。”|
|仍需调查|“关于登录失败：目前还不能确认原因。大约几点发生，页面显示什么提示？”|
|需求需澄清|“关于按日期导出：主要是哪些岗位使用，现有导入方式哪里不方便？”|
|故障尚无充分依据|“关于登录失败：已核对现有材料，仍缺失败时间及页面提示，暂不能判断是否为系统缺陷。大约几点发生，页面显示什么提示？取得这些证据后继续原授权内的只读排查，当前不新建 Bug Issue。”|
|已证实自身缺陷且需改代码、登记已读回|“关于列表空状态文案问题，已登记为蜂巢Issue #N，待负责人评估。① 静态代码在无筛选时仍显示有筛选提示，与已核对的产品规则不符，支持提示条件分支存在缺陷，需要修改代码，修复方向是修正条件判断。② 尚未核验现场部署版本，实际影响范围仍待确认；下一步在已有授权内核对部署依据，不表示已开始修复。”|

只有新单实际写入并核验成功才说“已登记”；登记不等于采纳、排期或开工。本人审批正文、私聊和无关日志不转发群。具体处理见 [群入口](GROUP_INTAKE.md)。

## 本人通知

首行或开头写 **项目名、事件类型、Issue 编号及必要短事项**，使脱离上下文也能理解；有 Issue 就附链接，未建单明示而不编造编号。通常三至五行，重点是目标、交付、风险、结果或待决定项，不堆机器字段。

以下 #42 均为合成事项；部署位置须从实际方案取得，不能套用示例。

```text
蜂巢｜需求评审 #42：登录页标题显示不准确（附 Issue 链接）。
建议只调整公司名称，保持布局和登录功能。
是否采纳这项需求？本条不请求执行批准。
```

```text
蜂巢｜执行方案 #42：调整登录页标题（附 Issue 链接）。
测试通过后提交推送、开 PR；本方案不含合并或部署。
影响仅限文案，完成后回写该 Issue，不自动关单或改台账。
可以按这个完整范围做吗？
```

```text
蜂巢｜交付结果 #42：标题已修改、测试通过并提交 PR（附链接）。
实际交付范围为文案及相关回归，尚未合并、未部署。
下一步：评审 PR；环境验收仍待后续授权。
```

## 自然表达与执行依据

对唯一、有效的完整计划，“可以，做吧”可表达同意，不要求复述固定口令；仍须分别核验意图、关联和真实权限。疑问、引述、历史同意和合成示例不产生许可；“继续”只续原授权有效剩余部分，不能开启自动开发或重做交付。

批准快照留在现有审计记录，示例不能代替实际计划。一次批准覆盖列明的范围，实质变化再核对；细则统一见 [核心流程](WORKFLOW.md)。
