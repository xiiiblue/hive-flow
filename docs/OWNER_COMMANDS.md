# 本人交互与简洁中文通知

由智能体理解研发意图，不要求用户记忆桥接业务命令或 UUID。以下是沟通示例，不宣称当前线上已有原生解析，也不授权规范之外的操作。实际账户、来源和工具权限须先核验。

## 手动推进

用户可以说“准备 #42 的方案”“按这个方案执行”“查询 #42”“停止 #42”。智能体把具体版本、范围与用户本次指令关联；有歧义时只澄清缺失部分，不猜任务。

方案先用短消息说明问题、拟改范围、检查和交付目标。若包括推送、合并及部署，一次写清目标分支、指定环境、验收和回滚；一次批准覆盖已明确动作，不逐步重复确认。详细文件和技术依据放到可追溯计划，按需展开。

旧 `/review` 只记录决定；“采纳”本身不表示启动开发。已经明确的执行授权也不能因一句转述、来源标记或智能体自拟 JSON 被扩大。

## 自动模式

示例：“未来三天，按已确认范围推进仓库 X 中已采纳的事项，允许测试后推送、合并并发布到指定开发环境，结束后停止。”

智能体核对明确截止、仓库、事项选择规则、操作/环境、额度与恢复要求，再通过已授权宿主原生任务执行；不是要求用户逐个发“自动入队”。“查询自动”只报告现场，“停止自动”阻止后续任务并协作核实活动任务的终态。

## 通知模板

```text
#42：已采纳，尚未启动。
下一步：准备范围内的实施计划。
```

```text
#42：测试通过，已合并并部署到获批开发环境。
验证：页面与健康检查通过。
遗留：用户端验收待确认。
```

```text
自动会话已暂停：额度读取不可用。
现场：当前任务保留占用，未继续部署。
下一步：核对额度和任务终态，再按有效授权恢复。
```

模板只示意表达，不是本次真实结果。清楚区分“已请求停止”“实际已停止”，以及“已发送”“接口确认”“用户已看到”。不默认展示 UUID、凭据、原始正文、堆叠日志或一大段协议字段；需要恢复关联时提供最小编号和详情入口。

## 消息能力是迁移门槛

主动发送本人审批、把回复关联到正确计划、超时后延续以及重复投递处理必须真实验证。旧 kind=issue 线程会在 generic bridge 下失败关闭；现有通用 [wecom:owner] 不能替代主动审批。不能仅改消息模板或复用一个过期通用线程就声称能力已接通。历史精确命令语法见 [旧应用存档](LEGACY_APPLICATION.md)，不作为可移植规范的强制入口。
