## 1.HiveFlow解决什么问题

用户在群里说“导出少了一页”，到问题真正解决，中间还需要调查现象、登记事项、决定是否采纳、明确实施范围、开发与审阅、部署与验收，最后把结果带回。任何一环缺少记录，后来的人就可能不知道谁同意了什么、现在进行到哪里，或者用户到底能不能用。

HiveFlow是一套让人和智能体共同完成这段工作的协作方法。它连接反馈、决定和交付，让每一步都有足够的依据，也让使用者不用在不同工具之间反复转述。

它复用dots、GitHub、Codex和消息桥接，不要求增加新的常驻调度服务。工具名称不授予权限，聊天中的建议也不自动变成开发指令。

本书用一条合成的“导出只包含当前页”案例贯穿主要流程，解释正常路径和异常处理。阅读后应能回答：

- 用户怎样反馈，接收方怎样调查，什么时候需要登记事项。
- 负责人怎样采纳、授权或暂停，已有授权内怎样连续推进。
- 执行者选择PR待审还是完整交付，每种模式怎样结束。
- 合并、部署、验收、正式登记与原群回执分别需要什么依据。
- 原生自动化怎样配置、选单和认领，哪些能力仍需真实验证。
- 网站怎样根据本书整理内容，并保留来源版本和适用范围。

## 2.与蜂巢、ACDL和网站的关系

蜂巢是这套方法形成和实践的项目背景。ACDL负责需求、设计、实施、评审和版本的工程协作；HiveFlow负责反馈入口、采纳与授权的衔接、任务交付终点及原来源回执。需要了解工程方法时，可以并读[ACDL研发流程手册](https://github.com/xiiiblue/hive-os/blob/a3e7c38a12b26c2b19a8a687c169c778e1bbe4f6/docs/11-手册/02-研发流程手册/README.md)。

HiveFlow的唯一权威执行规范在[自动化目录](../../06-自动化/README.md)。本手册将规则解释成连续教程和案例；独立[flow网站仓库](https://github.com/xiiiblue/flow)应以本手册为原始材料，整理[展示网站](https://www.bluexiii.com/flow/)的公开内容。

独立[hive-flow仓库](https://github.com/xiiiblue/hive-flow)已于2026-10-20按[Apache-2.0](https://github.com/xiiiblue/hive-flow/blob/main/LICENSE)开源，提供规范参考副本、介绍与离线工具。公开读者不需要访问私有HiveOS即可学习和试用；业务实例的源码访问、执行授权与启用状态仍分别核验。

内容依赖为**HiveFlow规范→HiveFlow介绍→HiveFlow网站**，维护规则由[HFL-016](../../06-自动化/HFL-016-文档维护规则.md#规范介绍与网站的依赖顺序)定义。规范改变时，先确认正式规则，再同步手册和网站。网站介绍不反过来授权真实操作，也不能替代项目当前记录。具体取材范围、章节映射和来源版本要求见[附录C](15-附录C：网站取材与内容维护.md)。

## 3.Issue之后：在MacMini上选择怎样启动、做到哪里

蜂巢当前以GitHub Issue作为云端与本机之间的研发交接点。云端Dots（本书沿用名称dots）接收反馈、调查并登记事项；Issue创建并核验后，后续研发由Director的MacMini上的Codex承接。源头的采纳评审仍记录其真实决定，本地执行则按实际手动授权或原生定时配置推进，不由云端dots逐步派发。

本节解释[HFL-003定义的本地启动方式](../../06-自动化/HFL-003-协作流程与授权.md#issue交接与两种本地启动方式)及[Director介入时点](../../06-自动化/HFL-003-协作流程与授权.md#director介入时点)。在MacMini上，有两个独立选择：**手动或定时决定怎样启动，PR待审或完整交付决定做到哪里。** 它们可以组成四条路径：

|启动方式|PR待审|完整交付|
|---|---|---|
|手动|Director在本机下达任务；Codex完成开发、检查和PR后停止，Director再介入一次，决定并推进合并、部署|Director明确完整范围并授权；Codex连续完成必要审阅、修正、合并、约定环境交付、验收和收尾|
|原生定时任务|本机任务在已批准且实际启用的配置内定时选单，完成PR后停止；Director仍需再介入一次处理合并、部署|本机任务在有效配置内选单并按完整终点推进，无需Director逐单再手动发起或例行确认后续步骤|

PR之后的介入，可以由Director自己操作，也可以在MacMini的可信执行会话中明确授权继续。完整交付中的代码审阅和业务验收仍需真实完成，但不天然要求Director本人逐步点击确认；约定由本人验收或出现超出授权的情况时，另行处理。

这张表描述路径，**当前业务自动执行尚未启用**。Issue存在不等于可以开工；新采纳模式仍需有效配置、受控决定及认领。Director的介入次数按本地研发阶段单独统计，源头采纳与定时配置准备另计，详见[第3章](03-流程总览：一条反馈怎样走到交付.md#9director需要介入几次)。

## 4.先看清三件容易混淆的事

**采纳表示值得做，实施授权说明可以做到哪里。** 已采纳的事项仍可能等待目标、环境或验收范围；已有明确授权时，则在该范围内连续推进，不为例行步骤反复确认。

**PR待审与完整交付是两个不同终点。** 前者形成供审阅的候选，后者在明确范围内完成必要审阅、合并、部署、验收、正式记录和结果反馈。写完代码不等于完成后者。

**业务完成与通知结果分别核验。** 部署和验收有自己的证据，消息受理、平台确认、用户收到与已读也有各自依据。通知失败不触发重复开发，结果未知先核实原动作。

## 7.当前能力与阅读边界

现行规范定义了手动交付和受控自动路径，已有模板、离线检查以及部分手动交付、单次原来源回执实践。**业务自动执行尚未启用。** 不能把“已有文档”或“模拟测试通过”解释成采纳后自动完成全链路已经验收。

实际控制记录、原生任务、权限和真实链路要分别核验。带日期的接入事实与未验收范围见[HFL-019](../../06-自动化/HFL-019-接入与验收记录.md)，怎样阅读这些证据见第12章。本书不会把历史状态直接当作所有环境的当前状态。

本书12章正文和3篇附录均保持Review状态。案例是合成材料，不代表产品承诺、真实授权、已完成开发或已通过验收。网站已公开，采用内容与发布状态按网站仓库的来源记录及实际页面核验，本手册不代表网站的实时版本。
