# HFL-005：事项状态与收尾

> 文档状态：Accepted
>
> 责任角色：Director
>
> 本文负责：定义评审、处理进度、正式登记身份及各入口的写入边界

对同一事项分别记录**评审状态、处理进度和正式登记身份**，另记执行授权及交付证据。聊天中的决定不能只停留在聊天，但也不会自动授予GitHub写入、关单或正式台账权限。来源、原事项和现有事实先核验，不重建已存在的单。

本页完整决定摘要、评论或收尾动作仍须分别获准；下述待确认流程的单项采纳答复只授权更新评审状态字段，不能套用其他行扩大写入。

## 决定与状态如何对应

评审决定、处理进度和正式登记身份分别按下述 [三个独立维度](#状态维度与同步契约)记录，不能把它们合成一个状态序列。实施授权及提交、合并、部署等交付事实另有证据；它们不是新增进度状态。

在建单前就按 [群入口](HFL-004-群反馈处理规则.md)直接拒绝的内容，不为“记录拒绝”再建新单。已有事项的拒绝不能通过只在群里说一句来假装GitHub已收尾；同样，Issue仍open也不能抹去已经确认的拒绝决定。

## 哪个入口可以写

|入口|可做什么|不能据此做什么|
|---|---|---|
|群反馈入口|达到建单条件后在已有授权内创建待确认新事项，无需等待采纳；命中旧单时回报关联|修改旧单正文/评论/标签、重开或关闭；群身份或引述批准不升级权限|
|dots本人主对话的单项采纳答复|仅按下述窄流程更新可靠关联Issue的评审状态并读回|借此改其他正文／评论／标签、开发、部署、关单或写正式台账|
|只读小时扫描|核对现有决定、交付与状态差异，汇总待处理项|借“补漏/同步/自动收尾”写Issue、改状态或正式台账|
|负责人本人主对话的具体任务|在明确列出的回写/关闭范围内，核验后完成并读回；同范围已获准步骤不重复询问|把一次任务权限沿用到未来扫描、其他事项或其他入口|

范围不足就把剩余动作列为待授权；写入失败则报告失败，结果未知先读回，不能重发评论或重复关单。不要为绕过限制更换账号、入口或工具。采用Dots时，本人主对话是当前适配；规范通用要求是唯一可核验的负责人决策通道，其他宿主须先验证其对应能力。

### 状态维度与同步契约

只使用以下三个独立维度，不新增一串平行标签，也不由状态文字授予工具或实施权限。

|维度|取值与含义|
|---|---|
|评审状态|`待负责人确认`／`已采纳（待实施授权）`／`暂缓`／`不采纳`，只回答是否采纳；与进度和正式登记身份独立|
|处理进度|沿用下表HiveOS八态，描述事实／范围确认、分流、处理及验证等实际进展；不得用评审决定或登记标记代替|
|正式登记身份|仅区分未关联或已关联真实 `ISSUE-xxxxxx` 正式事项；GitHub编号不可按数字猜正式编号，须核验真实映射。`status:Unregistered` 仅表示未关联，不是进度或采纳状态|

|处理进度|含义与边界|
|---|---|
|Reported（待确认）|事实／范围待确认，不等于评审状态中的“待负责人确认”|
|Triage（待分流）|确认应由何处承接、如何分类|
|Ready（待处理）|目标、方向与验收明确，尚未开始；不授予实施许可|
|In Progress（处理中）|实际处理在进行，必须注明是已授权只读调查还是获准实施，不能混写|
|Verification（待验证）|处理结果仍需按约定验收，提交／合并／部署事实不能代替验证|
|Closed（已关闭）|验收满足且有相应收尾权限后才关闭，不以合并或健康状态代替|
|Not Planned（不处理）|处理进度的结项选择，须有对应处置及收尾授权；评审“不采纳”不自动转入或关单|
|Duplicate（重复）|指向已核验的真实承接单；不凭相似标题或猜测关联，关闭等仍按实际授权|

已关联正式事项的处理进度以正式台账为准，在相应同步授权内单向同步至GitHub，不从GitHub反写台账或改写其权威进度。独立评审字段不混入台账同步的受管摘要，更新评审状态不得破坏该摘要。未关联项不能伪造正式编号；旧显示 `登记状态：待登记（尚未进入正式台账）` 与已有标签仅表达未关联身份，不构成第四个状态维度。

暂缓保留真实处理进度，在获准位置注明恢复条件；条件未知如实保留未知，不虚构排期或自动创建定时任务。不采纳仅是评审决定，不自动关闭Issue；关闭、Not Planned等处置仍核验当前实际授权。具体实施许可须来自可靠关联方案的范围与证据，采纳或Ready均不等于可实施。提交、合并、部署分别记录为交付事实，合并不等于验收完成。

群Bug入口只在调查后证据支持蜂巢自身缺陷且需要改代码时建单；HiveOS内部通用调查事项可按自身既有规则有更宽的建单口径，不能将其套到群Bug入口，也不以群入口门槛覆盖内部事项。新需求按原评估流程。先查、先原群反馈以及达到门槛直接待确认建单的顺序不变；等待评审不阻塞已授权调查。

以上是状态与同步契约，不授予实际Issue、标签或台账写入权限。旧单仅识别差异，不批量回填、关闭或重开，不重放旧事件；单项评审状态更新仍受下面窄授权约束。

### 群反馈待确认与单项评审

群反馈的待确认流程：Bug仍须先调查，仅证据支持蜂巢自身缺陷且需要代码修改才建单；新需求按原评估条件。达到条件后可直接创建临时状态Issue，无需等采纳批准。正文单独设置 `评审状态：待负责人确认`，保留 `登记状态：待登记（尚未进入正式台账）`，沿用已有 `status:Unregistered` 标签，不新建标签，也不把它当采纳或开发状态。“已登记为蜂巢Issue”仅表示Issue创建已读回，不表示进入正式台账。

先完成原群编号、脱敏初步分析及待确认回执，再在dots原生本人主对话发起对应Issue的单项采纳问询。未答复保持待确认，不阻塞其他群反馈或仍在原授权内的只读调查；正式工具拒绝、停止与数据风险限制照常遵守。

本人主对话当前答复可靠关联唯一Issue，且真实工具允许时，当前明确授权只覆盖将该Issue正文的评审状态按同意／不同意／暂缓更新为 `已采纳（待实施授权）`／`不采纳`／`暂缓`，随后独立读回。保留登记状态、标签、其他正文和开关状态；不追加评论、不自动开发、部署、关单或改正式台账。不明确就最小澄清，不能猜最近事项；自动化事件本身不消费历史或企微批准，不从无答复推定同意。此窄授权不授予群入口或只读扫描旧单编辑权，不批量回填旧Issue，也不恢复停用任务。

创建、发送或状态更新结果未知先核验真实结果，不盲重试；已完成不重放。更新前读当前正文，出现冲突或无法安全保留其他改动时停止对应写入并报告，不整段覆盖。

另外明确批准的本人主对话可按[受控采纳记录](HFL-010-采纳记录与任务认领.md)生产固定单槽；这不扩展本页群入口/自动扫描/receipt的写入权限。后续“只回复采纳”能否入选，取决于 [预授权自动配置](HFL-003-协作流程与授权.md#采纳与预授权自动配置)是否已获本人授权、完整且启用，以及dots受控生产背书和原生任务能否按固定单槽核验配置、决定及认领。采纳字段含义及本页单项正文写入范围均不变；不据此给intake新增派发、评论、标签、队列或执行权。无配置、未启用、历史采纳或受控记录未知时不执行，不能仅凭Issue正文或外部材料伪造入队批准。

## 可照做的收尾顺序

1. 核对固定仓库和原事项、负责人真实决定及当前授权。先看既有评论/正文/状态，排除别人已完成的收尾；不因扫描记录缺失就重写。
2. 准备适合目标仓库受众的简短摘要：决定或交付、依据、范围、下一步/剩余项、时间与证据。不复制私人审批原话或群记录。
3. 仅在授权内，把决定写到约定位置；已有决定段和新评论不能互相矛盾。按当前事实区分“采纳”“不采纳”“暂缓”“交付待验收”等；不制造相反的标签或虚假排期。
4. 如获准关闭且标准满足，关闭原事项；保留必要来源标记和无关标签，不顺手改其他Issue。暂缓不关，部分交付不冒充全部完成。
5. 独立读回评论/正文中的决定及真实开关状态；只凭写入调用返回不报成功。报告已写、已关、待授权、失败或未知各自状态。
6. 正式台账只在任务明确列出文件/字段和写入许可时更新；否则留待办。不要因写了Issue就自动改台账、恢复执行许可或触发开发。

例如，一个已有需求被明确不采纳，若本人主对话同时批准更新决定段、记录评审结论和关闭，便按原单核验、记录、关闭、独立读回完成；不是要求群入口或只读扫描获得同样权限。

## 结项检查

- 决定、实施许可、交付层级、Issue开关状态分别有依据，没有把采纳当实施批准。
- 可写位置中的摘要与状态一致；无法写入的差异明确列为待办，没有留成“无人知道为何open”。
- 实际验收、部分未完成和未实测分别说明；拒绝／暂缓未被当作新增实施许可，交付没有凭健康或合并提前关单。
- 回写/关闭已独立读回；未知结果先核验，其他人的既有收尾不重复执行。
- 无无关标签/事项/正式台账改动；没有新增自动化权限。

这些是规范与检查要求，不是自动执行器。文档更新本身不会同步或提升现有任务提示和权限，见 [核心流程](HFL-003-协作流程与授权.md#收尾与规范同步)。
