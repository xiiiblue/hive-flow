# HFL-007：HTTP回执接口

> 文档状态：Accepted
>
> 责任角色：Director
>
> 本文负责：规定当前Webhook通知与发布恢复，保留旧HTTP契约供历史核对

2026-10-30起，新任务使用Hermes和固定群Webhook；当前规则见下面新入口，原Dots/Slack/bridge说明只保留为历史协议。

## Webhook通知入口

当前固定群公告通过企微HTTPS Webhook直接发送，不依赖Hermes模型、Slack或bridge。QueenBee负责交互，消息推送身份负责主动通知。本人配置准确项目、用途与群后才能启用，测试群和正式群分开；项目与正式群必须一一核验，不能从群名猜测对应关系。真实Webhook只放运行机器的0600私有配置，不进入Git、日志和证据正文。

HiveOS发布入口支持`~/.config/hive-os/dev-deploy-notices.json`中的Webhook配置：`transport=wecom_webhook`、`repository=xiiiblue/hive-os`、`name=dev-deploy`、`webhook=<本人批准的完整HTTPS地址>`。原bridge配置只保留历史兼容，不自动切换未收尾的旧发布。地址必须为企微固定主机的webhook/send路径，不跟随重定向。MacMini或远程开发机都可运行同一正式发布入口，各自受控保存配置和通知记录。

本地通知账在网络提交前固定受众指纹、正文摘要及稳定deliveryId，企微errcode=0记wecom_ack，明确错误记rejected，超时/断线/崩溃记unknown。Webhook没有服务端状态查询或幂等接口，本地status只能返回已保存证据，不声称平台重新确认。已尝试/未知不自动重试，改变正文、受众或从另一机器接棒均先核验原记录；每次只允许一个执行者。换配置不能把原通知转投另一个群。

发布公告继续遵守北京时间工作日08:00（含）至18:00（不含），时段内开始ACK后才部署，完成公告等实际发布及约定验收；时段外新通知跳过、不补发，已尝试的未知不能伪装为跳过。开始、完成、失败与Issue阶段回执各有稳定编号。无变化、计划和演练不发公告，不为测试公告执行发布。

首次启用前核验旧通知账无在途/未知、两机占用和明确受众。撤回只恢复配置及代码，保留所有发送记录，不删除账或恢复旧库重放。原始测试成功只能证明该次接口受理，实际收到和用户已读分别记录。

### 文本回执与成员提醒

[正式事项回执](HFL-006-研发交付与原群回执.md#即时答疑与正式回执)使用企微Webhook的`text`消息，正文放在`text.content`，本单提出人的已核验标识放在`text.mentioned_list`。按私有来源和本人批准的目录精确匹配，优先使用已有且在该Webhook通道验证可用的ID；不能仅凭ID前缀或其他通道的失败就要求改为内部账号、手机号或重新整理整份名单。确需转换时，另核对接口权限和本人授权，不扩大通讯录访问。

消息中只包含该事项所需的脱敏结论；成员标识仅作为平台提醒字段，不把原始ID、名单或Webhook密钥拼进可见正文。禁止使用`@all`或提醒无关成员。普通文字中的“@姓名”及智能机器人长连接中的`<@...>`写法不能作为Webhook真实提及的成功证据；不同通道与消息格式分别验证。

按[群回执的表达与分段](HFL-006-研发交付与原群回执.md#群回执的表达与分段)先生成可读正文，再交给JSON序列化库编码。正文字符串的段间使用真实换行，通常连续两个换行形成空行；JSON线上编码出现`\n`是正常转义，但解析后的`text.content`必须恢复成真实换行，不能成为反斜杠与字母n两个可见字符。发送前在本地解析实际请求，核对正文逐字一致、段落与空行保留、无双重转义，并保持`mentioned_list`与正文分开。这项校验不发送消息、不重放既有回执，也不改变发送账中的已固定正文摘要。

发送前在既有私有通知记录固定项目、来源群、阶段、稳定`deliveryId`、收件人集合和完整请求摘要，先保存提交状态，再提交一次；收件人变化也属于请求变化，不能绕过冲突检查。沿用本节的unknown停止规则，不因补提醒而重发已接受或结果未知的回执。Webhook返回`errcode=0`、原群实际显示成员提及、收件人确认收到提醒分别记录；未核验的结果保留未知。测试只在本人明确指定的群和成员范围内进行，不为验收重放旧业务回执。

### 快捷通知脚本

在已获准的业务仓库中，单条人工通知、事项回执及指定成员提醒优先使用`scripts/hiveflow/wecom_notify.py`，不再临时编写发送器、遍历仓库或聊天记录查人。日常操作只需本节、本人私有配置与该次通知事实，不展开Issue研发路线或整套部署文档。脚本不生成发送授权，不替代Issue来源、披露范围、发布时段及事实核验；用户已明确要求立即发送的独立通知按该次授权执行，不等待例行代码或文档收尾。

首次配置保存到`~/.config/hive-os/wecom-notify.json`，由本人持有、权限0600、普通文件。配置将准确项目、群、既有Webhook配置、获准成员目录和原有通知账固定下来，只有目录可选SSH读取；不能把姓名当userid或从普通系统账号猜测成员标识。以下均为合成占位，实际值不进Git：

```json
{
  "repository": "example/project",
  "group": "示例工作群",
  "webhook_config": "~/.config/hive-os/dev-deploy-notices.json",
  "directory": {"ssh_host": "example-dev", "path": "~/private/wecom-directory/contacts.json"},
  "ledger_dir": "~/.local/state/hive-os/manual-notices",
  "cache_dir": "~/.local/state/hive-os/wecom-member-cache",
  "cache_ttl_seconds": 86400
}
```

`webhook_config`复用既有0600配置中的`transport=wecom_webhook`、同项目`repository`和`webhook`，不在命令行传密钥。成员目录是含`name,userid`的JSON数组；本地目录省略`ssh_host`。SSH仅执行固定读取程序，只返回明确请求姓名的记录，不下载整份通讯录。首次精确匹配后将所需成员缓存到本人独占目录；缓存按项目、群、Webhook指纹及目录来源隔离，默认24小时，最多7天。姓名不存在、重名、缓存失效且来源不可读时停止；目录变动用`--refresh-members`重新读取，不猜ID或退成正文“@姓名”。

```sh
  # 预览完整正文、提醒姓名、请求摘要及已有结果，不发送群消息。
python3 -B scripts/hiveflow/wecom_notify.py plan --delivery-id example:result:1 --text-file /tmp/notice.txt --mention 示例成员甲
  # 已有授权和准确最终正文时，单条命令发送一次；多个提醒逐项重复--mention。
python3 -B scripts/hiveflow/wecom_notify.py send --delivery-id example:result:1 --text-file /tmp/notice.txt --mention 示例成员甲
  # 只读本地账，不读取成员目录、不连接Webhook，也不声称平台重新确认。
python3 -B scripts/hiveflow/wecom_notify.py status --delivery-id example:result:1
```

`--text-file`按UTF-8原字节读取，保留真实换行与空行，不从过期草稿恢复已删除内容；预览会显示正文，不能把秘密写进通知。`--expected-sha256`可在发送时固定已审核的完整请求摘要，正文或提醒集合变化即拒绝。`--offline`只允许命中本地缓存，用于无外部查询的预览和测试；`plan`默认不发送群消息，但首次或过期时可能只读查询获准SSH目录。

通知账复用`ledger_dir`并识别以前人工脚本保存的`deliveryId`，不会因换脚本另建空账重放。完整请求摘要覆盖正文和`mentioned_list`，发送前排他写入unknown并同步磁盘；并发只有一个提交者。已有wecom_ack、unknown或rejected只返回原结果，不自动重试，换正文、提及、项目或目标的同编号请求拒绝。另一机器接棒仍先取得原账，不能把本机文件互斥当成跨机锁或企微幂等。

源实例可在既有授权内使用真实传输；公开hive-flow副本无条件关闭HTTP发送及SSH成员读取，仅保留本地预览、查账和合成测试。脚本就绪不代表新群、通道或周期通知获准启用。

### 当前发布操作与恢复

`pnpm dev:deploy`在计划有变化时读取本人独占的本地通知配置；`--plan`、迁移试跑及无变化不通知。每次发布保存稳定编号及开始/完成/未完成三个阶段。各阶段提交公告前分别按`Asia/Shanghai`判断时间，时段外记录`skipped_outside_hours`，不提交、不等待下个时段、不补发；发布仍按原检查继续。时段内提交的开始消息须取得企微ACK后才部署。正式部署检查及远端成功组件核对通过后才处理完成消息；还需页面验收时使用`--defer-completion-notice`，验收后沿同一编号执行`--complete-notice=<编号>`，不再次部署。失败按实际阶段说明未完成部分，并按[回执表达](HFL-006-研发交付与原群回执.md#群回执的表达与分段)写清有证据的原因、用户影响及下一步；原因未知就点明当前卡点，不用固定安抚句代替事实。失败公告同样受时间限制，完成公告仍须满足原检查及验收条件。

自动发布入口在首次提交失败公告前，读取本次候选、本次尝试的失败依据，提炼可向群公开的原因和下一步；不把异常堆栈、凭据、内部身份或完整日志发群。读不到或无法确认属于本次的记录时，说明缺少哪类依据及下一步核对对象，不借用旧失败原因，不推断旧版本仍可用。自动公告不能固定回“正在核对现场，请等待后续结果”；如脚本无法满足这一要求，应修正信息传递与正文生成，并用离线失败场景验证，不能只修改示例或依赖执行者记住补充。

通知状态与部署状态分开保存。未知发送只查原编号，不重发、换ID或换通道；已提交的开始通知未确认时停止部署，跨出时间窗口也不得改记为跳过；部署已成功而完成通知未知时保留成功事实。时间限制约束正式入口的新提交，不撤回平台已经接受或正在发送的消息。`--notice-status=<编号>`只查询；开始ACK延迟后，候选未变可用`--resume-notice=<编号>`继续原发布；部署进程中断时先核对原现场，收尾命令只会核验已成功的原组件，不重新部署。未知状态、拒绝、候选变化或未处理中断锁须保留证据处理，不编辑记录绕过。操作细节见[开发环境入口](https://github.com/xiiiblue/hive-os/blob/81376639ffedf5ad8754ae856658779daebc4d34/docs/05-环境/示例开发环境.md#61构建与发布)。

公告正文按本次真实结果组织，不强制照抄示例。仅更新工作台或管理台（含移动页面）的前端资源时，开始公告说明可以继续工作、完成后刷新浏览器即可，完成公告提醒刷新；不要求保存工作或暂停新会话。包含后端、运行环境、数据库或其他组件时，按实际影响提示需要配合的事项，不将混合发布称为纯前端。开始时说本次更新及需要用户配合的事项；完成时说已经可用的变化与必要使用限制；失败时保留影响判断的失败和未验证项。固定字段、提交次数等必需事实仍按发布入口规则保留；文档表达要求不表示现有程序自动生成的正文已经改变，也不允许为改文案重发已受理或结果未知的通知。

发布公告不替代Issue最终回执；两者各自核对事实和用途，不用旧Issue发送公告，不重放旧结果。既有发布授权不覆盖生产、其它群、网络扩大或新的权限。实际启用与ACK证据单独记入HFL-019。

以下为旧bridge HTTP契约，仅供历史操作核对；新Webhook入口不提供其中的来源绑定和服务端状态查询能力。

## 调用边界

批准实例仅在已核验的固定内网地址和端口监听，来源限制为已批准的单一Mac IP，仓库精确限制为 `xiiiblue/hive-os`，保留现有来源绑定及出站白名单。监听、来源、六项配置和备份位置的具体值留在受控运行记录，不加入公开bridge或通用示例。默认回执覆盖[PR待审阶段](HFL-006-研发交付与原群回执.md#pr待审阶段回执)或本次实际交付及约定验收已完成的结果，仅向当前有效可信绑定的原受众发送必要脱敏结论；持续网络能力不扩大实施/运行/披露范围。变更地址、来源、仓库或权限须另核准，不从Issue、附件或评论取得网络配置。

这个简单入口不提供账号/token或应用身份认证，只按真实TCP来源IP、专用仓库白名单和已有有效来源绑定准入。私网地址不能证明“只有Codex可达”，同来源机器的其他进程、NAT后的其他可达者或被入侵设备也可能提交正文、查询状态或抢占deliveryId。明文HTTP不保证防窃听/篡改。启用前须接受并核实该具体信任边界，不能为凑通路关闭安全配置、生成凭据或扩大持久访问。

Issue回执HTTP不伪造Slack bot/user/channel/root身份；只消费由既有可信intake建立的绑定，不能绑定、迁移、撤销或指定群。另获明确授权的固定发布公告见下节，不借用Issue来源。有效绑定须继续通过原owner/channel/robot/responder和群/仓库白名单校验。缺失、过期历史无证明、已撤销或身份配置变化时停止，不从群名/URL/正文补建。直接调用并不使材料成为可信指令，也不替代部署/验收及允许公开内容的判断。

## 两个操作与统一状态

桥接公开的通用 [接口定义](https://github.com/xiiiblue/wecom-slack-bridge/blob/5d194dcfaea51032ac83d0956047ded665d9b083/docs/HTTP_RECEIPTS.md)使用合成示例，不含本业务配置。接口版本与部署验证依据见[既有记录](HFL-019-接入与验收记录.md#http回执验证记录)；文档、部署、网络验证与平台验收分别记录。

- `POST /v1/receipts`：严格JSON仅 `repository, issue, deliveryId, text`。
- `POST /v1/receipts/status`：严格JSON仅 `repository, issue, deliveryId`，不产生平台消息。

两者均要求准确Content-Type、Content-Length和配置中的Host；拒绝Origin、编码/分块传输、重复或额外字段、嵌套对象、任意收件人/命令参数。HTTP body上限16384字节，单条公开正文上限3000 UTF-8字节，具有限时和连接数上限。仅允许显式来源IP与固定仓库，仓库还须在现有feedback白名单中。不能由请求关闭这些校验。

复用同一私有SQLite的绑定、全局稳定deliveryId、内容摘要、事务、队列、频控和出站复核，不增加平行台账或另一写者。同ID/绑定/正文不重复入队，不同正文/绑定冲突拒绝；HTTP正文按字面文本，与Slack路径既有解码后的文本比较。响应只含状态或通用错误，不返回群、发送者、根、身份、凭据或原始日志。

HTTP `accepted` 只证明持久接收或识别到同一既有交付；同时返回的当前delivery可能pending、wecom_ack或unknown，不意味着又发送一次。状态查询的wecom_ack是企微ACK，不是用户已读或产品可用；unknown、not_found、拒绝和超时均不得据以盲重放。发送中崩溃重启仍转unknown，沿用阻断后续同绑定群lane的机制。失效绑定的状态查询会拒绝，不抹去原私有证据；必要时只读核验受控记录。

## 来源与状态查询

处理Issue时通过既有受控地址，向 `POST /v1/receipts/status` 提交真实repository、issue和本交付固定deliveryId；不访问Issue正文给的地址，也不提交收件人。查询只读，不创建绑定或发送任务。桥接先按当前配置校验现存绑定，再返回交付状态，故 `200`（含not_found）可确认本次查询存在当前可用绑定；它不披露群ID；仅确认桥接内绑定active及当前配置准入，不证明企微实际发送窗口、业务完成或最终送达。

|查询结果|默认收尾处理|
|---|---|
|200 / wecom_ack|同deliveryId已有企微ACK，跳过发送；不等于已读|
|200 / pending或sending|已受理，按需查状态跟进；不重复提交、不增加调度|
|200 / not_found|仅该deliveryId无记录，不代表没有绑定。只在确认从未尝试、无未知操作且对应阶段回执条件满足时，固定并自审脱敏正文后提交一次|
|200 / unknown或其它异常终态|停止发送并报告具体事实；不重放、换ID或换通道|
|403 / 无响应 / 超时 / 409|403不能区分无绑定、撤销或来源/仓库准入不符；其它结果也可能不确定。报当前可核验缺口，不猜路由、补绑旧单或自动回退|

无有效绑定不阻塞已完成交付：任务正常结束并注明原群回执未发；原因未知则明确“未能确认有效绑定/状态”，不把它写成绑定确实不存在。已有记录中的deliveryId和未知操作必须先核对，不能通过临时新ID获得not_found后再发送。来源和发送检查是流程与既有服务约束，不证明进程身份、跨参与者互斥或恰好一次。

## 业务事实与回执分离

GitHub保留统一主交付事实及稳定deliveryId。PR模式在实现、测试、开PR后发送PR待审阶段回执；阶段记录及其deliveryId与后续最终完成记录分开，不发最终完成回执或 `HiveFlow delivery v1`。最终通知须满足原契约的真实关联合并commit、所需检查、实际部署或明确not_required、验收和本次授权；schema不扩展。业务证据/公开摘要由获准调用方独立核验，通用bridge不访问GitHub或批准业务。

新交付默认按 [单一通知路径](HFL-006-研发交付与原群回执.md#选择单一通知路径)使用HTTP，不再写PR完成唤醒标记或另请dots发送；若已选择PR→dots、标记已发或存在受理/未知状态，则不转HTTP接手。沿用同deliveryId、已审核正文和现有结果，未知先核实并向本人报告，不自动fallback或换ID重发。共享去重不是跨参与者锁或恰好一次保证。默认收尾规则不自动修改现行监听触发、自动任务或桥接配置，也不扩大实施、评审、合并、部署和运行权限。

通知拒绝、审批受阻、未知或无绑定不重做开发、不换入口重发；人工接手见 [通知非阻塞](HFL-006-研发交付与原群回执.md#通知非阻塞与人工接手)。特别是此前已被拒绝的合成发送，不能用新入口重试、搬运旧绑定/ID或扩大解释原许可。

## 固定开发发布公告

Director于2026-10-21明确要求示例开发环境正式开发发布前后通知指定企微群，并将通知时间限制为北京时间周一至周五08:00（含）至18:00（不含）。此项独立于Issue交付：复用原桥接进程、HTTP监听、来源IP、仓库范围、SQLite和发件箱，不新建机器人、凭据或调度，不补绑历史Issue。群名对应关系由本人提供的既有回执线索与当前有效绑定交叉核验，准确群ID仅保存在受控配置。

桥接新增默认空的`RECEIPT_HTTP_ANNOUNCEMENT_TARGETS`配置，每项仅含`repository,name,chatId`，仓库与群均须已在现有白名单。调用方只传固定公告名，不传群ID；首次提交固定受众及owner/channel/robot，之后改变配置不得把已有队列重定向。每次出站重新核验公告配置和身份；撤销后停止新出站，不承诺撤回正在发送的消息。

- `POST /v1/announcements`：严格JSON仅`repository,name,deliveryId,text`。
- `POST /v1/announcements/status`：严格JSON仅`repository,name,deliveryId`；查询不创建关联或消息。

与Issue回执共享全局deliveryId去重、正文摘要、事务、队列、频控、ACK和unknown规则。接口不理解发版、不批准业务、不执行命令；实际部署事实由正式发布入口负责。既有网络信任限制仍适用，同来源的其它进程也可能提交已允许的公告，不能宣称有应用身份认证。

旧桥接时期发布入口的业务约束延续到[当前发布操作与恢复](#当前发布操作与恢复)；本节仅保留退役HTTP接口定义，不启用旧发送。

## 升级与恢复

后续升级/变更仍核对唯一写者、实际来源与网络风险、一致备份及兼容回滚。回滚先停写、关闭HTTP并恢复旧代码/配置，保留升级后的队列与回执，不用旧库覆盖、不把unknown改pending。旧代码也可能继续处理已受理pending，回滚不等于取消发送；是否继续或沿既有获准路径撤销须先核实，不能盲重放。恢复演练是否实际完成，按HFL-019中的注明时间记录判断。
