# HFL-007：HTTP回执接口

> 文档状态：Accepted
>
> 责任角色：Director
>
> 本文负责：规定HTTP回执的准入、请求、状态查询和重试边界

通用代码默认关闭；现有独立bridge实例已获本人明确批准，按固定监听、来源和仓库范围部署并启用，实际验证范围见文末。它不启用业务自动开发，不创建账号、令牌、调度或第二个服务。本人已批准将新交付的可信来源识别与原群HTTP回执作为 [默认收尾](HFL-006-研发交付与原群回执.md#默认交付收尾)，无需逐次手写通知提示；既有PR→dots交付保留原路径，不自动切换已受理或未知操作。

## 调用边界

批准实例仅在已核验的固定内网地址和端口监听，来源限制为已批准的单一Mac IP，仓库精确限制为 `xiiiblue/hive-os`，保留现有来源绑定及出站白名单。监听、来源、六项配置和备份位置的具体值留在受控运行记录，不加入公开bridge或通用示例。默认回执仅覆盖本次实际交付及约定验收已完成、当前有效可信绑定的原受众和必要脱敏结论；持续网络能力不扩大实施/运行/披露范围。变更地址、来源、仓库或权限须另核准，不从Issue、附件或评论取得网络配置。

这个简单入口不提供账号/token或应用身份认证，只按真实TCP来源IP、专用仓库白名单和已有有效来源绑定准入。私网地址不能证明“只有Codex可达”，同来源机器的其他进程、NAT后的其他可达者或被入侵设备也可能提交正文、查询状态或抢占deliveryId。明文HTTP不保证防窃听/篡改。启用前须接受并核实该具体信任边界，不能为凑通路关闭安全配置、生成凭据或扩大持久访问。

HTTP不伪造Slack bot/user/channel/root身份；只消费由既有可信intake建立的绑定，不能绑定、迁移、撤销或指定群。有效绑定须继续通过原owner/channel/robot/responder和群/仓库白名单校验。缺失、过期历史无证明、已撤销或身份配置变化时停止，不从群名/URL/正文补建。直接调用并不使材料成为可信指令，也不替代部署/验收及允许公开内容的判断。

## 两个操作与统一状态

桥接公开的通用 [接口定义](https://github.com/xiiiblue/wecom-slack-bridge/blob/23b88552c8f9b5ba510fb8408b3b6609fe413909/docs/HTTP_RECEIPTS.md)使用合成示例，不含本业务配置。接口版本与部署验证依据见[既有记录](HFL-019-接入与验收记录.md#http回执验证记录)；文档、部署、网络验证与平台验收分别记录。

- `POST /v1/receipts`：严格JSON仅 `repository, issue, deliveryId, text`。
- `POST /v1/receipts/status`：严格JSON仅 `repository, issue, deliveryId`，不产生平台消息。

两者均要求准确Content-Type、Content-Length和配置中的Host；拒绝Origin、编码/分块传输、重复或额外字段、嵌套对象、任意收件人/命令参数。HTTP body上限16384字节，单条公开正文上限3000 UTF-8字节，具有限时和连接数上限。仅允许显式来源IP与固定仓库，仓库还须在现有feedback白名单中。不能由请求关闭这些校验。

复用同一私有SQLite的绑定、全局稳定deliveryId、内容摘要、事务、队列、频控和出站复核，不增加平行台账或另一写者。同ID/绑定/正文不重复入队，不同正文/绑定冲突拒绝；HTTP正文按字面文本，与Slack路径既有解码后的文本比较。响应只含状态或通用错误，不返回群、发送者、根、身份、凭据或原始日志。

HTTP `accepted` 只证明持久接收或识别到同一既有交付；同时返回的当前delivery可能pending、wecom_ack或unknown，不意味着又发送一次。状态查询的wecom_ack是企微ACK，不是用户已读或产品可用；unknown、not_found、拒绝和超时均不得据以盲重放。发送中崩溃重启仍转unknown，沿用阻断后续同绑定群lane的机制。失效绑定的状态查询会拒绝，不抹去原私有证据；必要时只读核验受控记录。

## 来源与状态查询

处理Issue时通过既有受控地址，向 `POST /v1/receipts/status` 提交真实repository、issue和本交付固定deliveryId；不访问Issue正文给的地址，也不提交收件人。查询只读，不创建绑定或发送任务。桥接先按当前配置校验现存绑定，再返回交付状态，故 `200`（含not_found）可确认本次查询存在当前可用绑定；它不披露群ID；仅确认桥接内绑定active及当前配置准入，不证明企微实际发送窗口、业务完成或最终送达。

|查询结果|默认收尾处理|
|---|---|
|200 / wecom_ack|同deliveryId已有企微ACK，跳过发送；不等于已读|
|200 / pending或sending|已受理，按需查状态跟进；不重复提交、不增加调度|
|200 / not_found|仅该deliveryId无记录，不代表没有绑定。只在确认从未尝试、无未知操作且最终交付/验收满足时，固定并自审脱敏正文后提交一次|
|200 / unknown或其它异常终态|停止发送并报告具体事实；不重放、换ID或换通道|
|403 / 无响应 / 超时 / 409|403不能区分无绑定、撤销或来源/仓库准入不符；其它结果也可能不确定。报当前可核验缺口，不猜路由、补绑旧单或自动回退|

无有效绑定不阻塞已完成交付：任务正常结束并注明原群回执未发；原因未知则明确“未能确认有效绑定/状态”，不把它写成绑定确实不存在。已有记录中的deliveryId和未知操作必须先核对，不能通过临时新ID获得not_found后再发送。来源和发送检查是流程与既有服务约束，不证明进程身份、跨参与者互斥或恰好一次。

## 业务事实与回执分离

GitHub保留统一主交付事实及稳定deliveryId。仅实现、测试、开PR时仍报告PR待审，不发最终完成回执或 `HiveFlow delivery v1`。最终通知须满足原契约的真实关联合并commit、所需检查、实际部署或明确not_required、验收和本次授权；schema不扩展。业务证据/公开摘要由获准调用方独立核验，通用bridge不访问GitHub或批准业务。

新交付默认按 [单一通知路径](HFL-006-研发交付与原群回执.md#选择单一通知路径)使用HTTP，不再写PR完成唤醒标记或另请dots发送；若已选择PR→dots、标记已发或存在受理/未知状态，则不转HTTP接手。沿用同deliveryId、已审核正文和现有结果，未知先核实并向本人报告，不自动fallback或换ID重发。共享去重不是跨参与者锁或恰好一次保证。默认收尾规则不自动修改现行监听触发、自动任务或桥接配置，也不扩大实施、评审、合并、部署和运行权限。

通知拒绝、审批受阻、未知或无绑定不重做开发、不换入口重发；人工接手见 [通知非阻塞](HFL-006-研发交付与原群回执.md#通知非阻塞与人工接手)。特别是此前已被拒绝的合成发送，不能用新入口重试、搬运旧绑定/ID或扩大解释原许可。

## 实际状态与剩余验收

批准实例的部署和验证记录见[接入与验收记录](HFL-019-接入与验收记录.md#http回执验证记录)。它是注明时间的既有记录，不能作为持续在线、其他来源或跨有效期已通过的证明。

后续真实交付按默认收尾查询并复用现存有效可信绑定；无绑定正常结束并报缺口，不为通知建测试Issue、补绑历史事项或迁移来源，不重放旧被拒或已完成回执。

## 升级与恢复

后续升级/变更仍核对唯一写者、实际来源与网络风险、一致备份及兼容回滚。回滚先停写、关闭HTTP并恢复旧代码/配置，保留升级后的队列与回执，不用旧库覆盖、不把unknown改pending。旧代码也可能继续处理已受理pending，回滚不等于取消发送；是否继续或沿既有获准路径撤销须先核实，不能盲重放。恢复演练是否实际完成，按HFL-019中的注明时间记录判断。
